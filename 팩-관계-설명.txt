도메인 팩(hynix_mydata) — 개념과 관계가 무엇을 뜻하나
=====================================================

이 문서는 그래프에 들어간 노드와 간선을 읽을 때 쓴다. 팩 파일을 고치는 방법은
02-도메인-팩.md 에 있다.


1. 그래프는 세 겹이다
---------------------

같은 인덱스 안에 성질이 다른 셋이 들어간다. 어느 겹에서 온 간선인지 알면
그 값을 얼마나 믿어야 하는지도 알 수 있다.

업무 그래프
  TMS, iFlow, Cube 의 CSV 필드를 그대로 옮긴 것이다. 담당자, 기한, 상위 업무
  같은 정형 정보다. 필드에 적힌 것을 옮기기만 하므로 틀릴 일이 없다.

개념층
  이슈 본문, 블로그 글, 대화에서 LLM 이 뽑은 것이다. 시스템, API, 이슈, 조치,
  결정 같은 것과 그 사이의 관계다. 사람이 쓴 문장을 해석한 결과이므로 신뢰도가
  값으로 붙는다.

연결
  위 둘을 잇는다. 어느 업무의 본문에서 그 개념이 나왔는지, 어느 대화가 어느
  이슈를 부르고 있는지를 잇는다. 이것이 없으면 질문이 업무 제목에 걸렸을 때
  근거로 쓸 문장이 하나도 없어서 답이 나오지 않는다.

같은 사실을 두 겹에서 중복으로 만들지 않는다. 담당자는 TMS 필드에 있으니
업무 그래프가 만들고, LLM 에게는 뽑지 말라고 지시한다.


2. 개념 타입
------------

LLM 이 뽑는 개념은 아래 아홉 가지 중 하나다.

System        시스템이나 모듈. TMS, CUBE, iFlow, 인증서버.
Api           API 와 인터페이스. /getContentsBody, 전송요구 API.
Feature       기능이나 화면. 동의 화면, 자산 조회.
Issue         이슈나 오류. 응답구조 불일치, 타임아웃.
Action        조치나 변경 작업. 응답구조 변경, 핫픽스 배포.
Decision      결정이나 합의. 우선순위 변경 결정, 구조 변경 합의.
Requirement   요구사항이나 요청. 필드 추가 요청, 규격 준수 요건.
Person        사람.
Topic         위 어디에도 안 맞을 때 쓰는 자리다(폴백).

Topic 으로 떨어진 개념은 그래프 노드로 만들지 않는다. 버리는 대신 기록은
남기는데, 그것이 팩에 어떤 타입을 더해야 하는지 알려주는 단서가 된다.

적재할 때 앵커 타입을 지정한다. 기본값은 System, Api, Issue, Decision 이고,
여기에 닿지 못하는 개념은 그래프에 넣지 않는다. 사번이 Person 으로 뽑혀도
걸러지는 이유가 이것이다. 사람과 개념은 업무 그래프와 연결 단계가 잇는다.

API 와 영문 경로는 표기를 바꾸지 않는다. /getContentsBody 를 한 번이라도
다르게 적으면 그래프에서 같은 API 가 두 노드로 갈라진다.


3. 개념층의 관계
----------------

LLM 이 뽑는 관계는 일곱 가지다. 괄호 안은 가중치와 신뢰도의 기본값이다.

causes (0.8 / 0.7)
  원인이다. 주로 Issue 나 Action 에서 Issue 로 간다. 추이 추론을 2단계까지
  허용한다. A가 B의 원인이고 B가 C의 원인이면 A와 C를 간접 원인으로 본다.

resolved_by (0.9 / 0.7)
  이 조치나 결정으로 해결됐다. Issue 에서 Action 또는 Decision 으로 간다.
  방향을 뒤집으면 조치가 이슈가 되므로 순서가 중요하다.

affects (0.8 / 0.6)
  영향을 준다. Decision 이나 Action 에서 Feature, Api, System 으로 간다.
  "이 결정으로 영향받은 것" 을 묻는 질문이 이 간선을 탄다.

requires (0.7 / 0.6)
  필요로 한다. Requirement 나 Feature 에서 Api, System, Action 으로 간다.

uses (0.7 / 0.6)
  사용한다. Feature 나 System 에서 Api, System 으로 간다.

part_of (0.8 / 0.7)
  구성요소다. Feature 나 System 에서 System 으로 간다. 추이 추론을 4단계까지
  허용한다. 시스템 계층을 따라 올라가기 위한 것이다.

related_to (0.5 / 0.5)
  관련이 있다는 것만 아는 경우다(폴백). 방향이 없다. 위 여섯 가지에 억지로
  끼워 맞추는 것보다 이쪽에 두는 편이 낫다.

이 밖에 discussed 가 팩에 선언돼 있지만 LLM 은 뽑지 않는다. 글이나 대화의
작성자 정보를 보고 적재기가 만든다.


4. 관계를 뽑는 기준
-------------------

문장에 명시된 것만 적는다. 추론해서 잇지 않는다. 두 개념이 같은 문단에
있다는 이유로 잇지 않는다.

근거가 필수다. 관계마다 어느 청크에서 나왔는지(번호)와 그 문장을 원문 그대로
적게 한다. 인용을 다듬으면 원문에서 위치를 찾을 수 없어 근거로 쓸 수 없다.

양쪽 개념은 주어진 개념 목록에 있는 표기를 그대로 써야 한다. 목록에 없는
이름을 만들면 어디에도 닿지 않는 간선이 생긴다.

실무에서 자주 나오는 두 형태를 지시로 못박아 두었다.

  "~하기로 했다, 그래서 ~가 바뀐다" 는 Decision 과 대상을 affects 로 잇는다.
  "해결됐다 / 정상 확인 / 조치 완료" 는 앞의 이슈와 조치를 resolved_by 로 잇는다.


5. 뽑지 않는 것
---------------

담당, 기한, 상위 업무, 업무 간 의존은 뽑지 않는다. TMS 필드에 있으므로
업무 그래프가 결정적으로 만든다.

TMS 이슈 키(MYDATA-123 같은 것)는 개념이 아니다. 연결 단계가 키를 찾아
해당 업무에 잇는다.

청크 맨 앞에 붙는 문맥 줄(업무공간, 분류, 라벨, 담당, 요청, 연관 업무)은
읽기만 하고 그 줄에서 개념을 뽑지 않는다. 뽑으면 "장애", "긴급" 같은
분류어와 사번이 개념이 되어, 그 단어가 들어간 모든 질문이 거기에 걸린다.

조사, 일반 동사, 잡담 어휘는 개념이 아니다.


6. 업무 그래프의 관계
---------------------

CSV 필드에서 그대로 만든다. 신뢰도 개념이 없다. 필드에 그렇게 적혀 있다는
뜻이다.

TMS 업무(Task)
  assigned_to    담당자
  reported_by    요청자
  watched_by     참조자
  blocks         이 업무가 끝나야 상대가 진행된다
  derived_from   상대 업무에서 파생됐다
  in_system      어느 업무공간(시스템)의 업무인가

  오라클에서 직접 읽는 경우에는 subtask_of(상위 업무)와 relates_to(연관 업무),
  in_space(공간)를 쓴다.

Cube 메시지(Message)
  authored_by    작성자
  replies_to     어느 메시지에 달린 답글인가
  in_space       어느 채널인가

iFlow 글(Post)
  authored_by    작성자
  in_system      어느 그룹의 글인가

blocks 와 derived_from 은 방향이 뜻을 가진다. 뒤집으면 선후가 바뀐다.


7. 연결 단계의 관계
-------------------

업무 그래프와 개념층을 잇는다. 간선은 두 종류뿐이고, 어떻게 이어졌는지는
derived 속성에 남는다.

mentions — 업무나 글이 그 개념을 다룬다

  provenance (0.9 / 0.9)
    그 개념이 이 업무의 본문에서 추출됐다. 개념의 근거 청크 이름이
    blog:<업무키>:cNNN 이면 그 업무에서 나온 것이므로 확실하다. 추론이 아니다.

  key_mention (0.6 / 0.6)
    개념의 인용문 안에 업무 키가 등장한다. 추론이므로 inferred 로 표시한다.
    TMS-12 가 TMS-120 에 걸리지 않도록 앞뒤가 단어 문자나 하이픈이 아닐 때만
    인정한다.

  name_match (0.7 / 0.7)
    개념 이름이 시스템 이름과 정확히 같다. 시스템을 가리키는 개념은 대화에서
    나오는 일이 많아 이슈 본문과 이어지지 않는데, 그러면 질문이 그 개념에
    걸렸을 때 업무 그래프로 건너갈 다리가 없다.

  assigned_task (0.5 / 0.5)
    그 업무를 담당한 사람에게도 같은 개념을 잇는다. 사람이 그 개념을 직접
    말한 것이 아니라 업무를 담당했을 뿐이므로 가중치를 가장 낮게 둔다.
    어느 업무를 거쳐 왔는지 via 속성에 남는다.

    이것을 넣은 이유가 있다. Person 노드에는 인용문이 없다. 사번으로 묻는
    질문이 Person 에 걸리면 모이는 노드가 Person 과 Task 뿐이고 근거가 0건이라
    답이 나오지 않았다.

  같은 (업무, 개념) 쌍에 여러 근거가 있으면 provenance 가 이긴다.
  메신저 청크는 대화 묶음 단위라 메시지 한 건과 1:1 이 아니므로 provenance 를
  만들지 않는다. 키 언급으로만 잇는다.

refers_to — 대화나 글이 어느 이슈를 부른다

  key_mention (0.7 / 0.7)
    메시지나 글 본문에 업무 키가 적혀 있다. 현장의 흐름은 대화에서 논의한 뒤
    TMS 에 등록하고 처리하는 것인데, 대화와 이슈가 끊겨 있으면 "어떻게
    처리했나" 가 대화에서 멈춘다.

업무 그래프에 없는 업무나 글에는 노드를 새로 만들지 않는다. 없는 것은 잇지
않고 넘어간다.


8. 그래프를 읽을 때
-------------------

간선의 derived 속성을 먼저 본다. 없으면 결정적(필드에서 온 것)이고, 있으면
무엇을 근거로 추론했는지 알려준다. inferred 가 true 면 추론이다.

가중치가 낮은 간선이 틀렸다는 뜻은 아니다. 간접적이라는 뜻이다.
assigned_task 0.5 는 "이 사람이 담당한 업무에서 나온 개념" 이고, provenance
0.9 는 "이 업무 본문에서 나온 개념" 이다. 둘 다 맞지만 질문에 답할 때의
무게가 다르다.
